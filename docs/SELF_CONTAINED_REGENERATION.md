# Self-Contained Regeneration Standard

| Header field | Value |
| --- | --- |
| **Question** | What must be retained, documented, and executed so that every promoted DAAD Harvester result can be regenerated from a repository clone without a hidden external application or service? |
| **Evidence scope** | Global implementation and promotion policy. It applies to P1 structural measurements, generated corpus evidence, reports, binary analyses, decompilations, and all claims presented as reproducible. |
| **Status** | permanent, mandatory, CI-enforced project directive |
| **Implementation links** | [`../preservation_corpus/regeneration_manifest.json`](../preservation_corpus/regeneration_manifest.json), [`../scripts/verify_regeneration_manifest.py`](../scripts/verify_regeneration_manifest.py), [`../scripts/check_docs.py`](../scripts/check_docs.py), [`../TODO.md`](../TODO.md) |
| **Non-claims** | A self-contained regeneration path does not independently establish historical identity, semantic correctness, or equivalent runtime behavior. It makes the exact claimed computation repeatable from retained inputs. |

> **Authoritative global directive — SELF-CONTAINED REGENERATION: REQUIRED.** No result may be promoted as a primary preservation, analysis, decompilation, extraction, report, or verification result unless a fresh repository clone can regenerate and verify it using only committed inputs, source-controlled code, declared dependencies, and a documented command. An external application, emulator, network endpoint, GUI tool, proprietary program, local cache, or unstated workstation resource must never be a silent primary prerequisite.

This is a global rule without platform, format, artifact, tooling, or project-phase exceptions. It governs all nine DAAD targets, source acquisition records, raw media, parser outputs, DDB evidence, interpreter identities, reverse-engineering outputs, static reports, TUI recordings, decompiler/compiler round trips, future behavioral evidence, and any later ScummVM-facing work.

## Regeneration classes

| Class | Permitted role | Mandatory retained material | Promotion consequence |
| --- | --- | --- | --- |
| **Repository-native primary path** | Produces and verifies the authoritative result. | Committed input hashes, source code, deterministic command, output hashes, tests, and a manifest entry. | Required for every promoted result. |
| **Declared dependency** | Supports the primary path through a versioned, documented package dependency. | Dependency declaration, version range/pin, offline-compatible installation path where feasible, and test coverage. | Permitted only when declared; it may not be an undeclared host executable. |
| **External independent validator** | Corroborates a result generated by the primary path. | Tool/version/configuration, invocation log, output hash, and an explicit statement that the result is non-primary. | Useful corroboration; never a requirement to regenerate the promoted result. |
| **Acquisition-only runtime** | Creates a new observation that is then retained as an immutable input. | Configuration, bounded command log, capture hash, provenance, and conversion/extraction script. | The runtime may acquire evidence, but a committed input must permit later regeneration without rerunning it. |

## Non-negotiable promotion gate

A promoted result must have all of the following. Missing any item keeps the output as an investigation record, not a primary result.

1. A committed input manifest with SHA-256 for every source byte, snapshot, fixture, configuration, and reference used by the primary command.
2. A repository-local command that does not download, open a GUI, invoke an undeclared executable, or read an uncommitted path.
3. A committed output hash or byte-for-byte comparison target, plus a CI-safe verifier that fails on drift.
4. A declared dependency list and an explicit `external_validators` classification, including an empty list when none exists.
5. A regression test covering command success and the expected evidence boundary, including negative/corruption cases where the format contract requires them.
6. Documentation linking the claim to its manifest entry and distinguishing any external corroboration from the native primary path.

## Manifest and enforcement contract

The machine-readable [`regeneration_manifest.json`](../preservation_corpus/regeneration_manifest.json) is the project registry for promoted paths. Each entry records its immutable inputs and outputs, the repository-local Python command, declared dependencies, network prohibition, and optional validators. [`verify_regeneration_manifest.py`](../scripts/verify_regeneration_manifest.py) validates all input/output hashes and executes only the explicitly supported local Python verifier shape. It refuses network-dependent entries and refuses commands that are not repository-local Python scripts.

[`check_docs.py`](../scripts/check_docs.py) requires this policy to be linked from project entry points, research methodology, evidence contracts, and corpus-handling policy. The continuous-integration workflow runs policy/documentation verification as a dedicated gate and executes the mandatory full test suite, which includes the manifest verifier. A contributor cannot remove the rule from a core document or add an unverified registered result without failing the relevant gate.

## External-tool boundary

VICE, Ghidra, radare2, c64tapedecode, platform emulators, disassemblers, browser sessions, and archive-site services remain valuable independent validators or acquisition methods. Their retained evidence is scientifically useful precisely because it is independent. However, a report generated only by one of those tools is not a self-contained primary result. The repository must retain the resulting bytes and implement a local parser, verifier, or conversion path that operates on those committed bytes before promotion.

For example, the committed Jabato C64 TAP reports are regenerated from retained TAP, RAM, and DDB evidence by a standard-library Python command. VICE contributed controlled acquisition-time RAM observations, and `c64tapedecode` independently corroborated the ROM bootstrap, but neither program is executed by the primary regeneration command.[1]

## Contributor checklist

Before opening a pull request or creating a preservation checkpoint, answer the following questions in the relevant evidence note and manifest entry.

| Check | Required answer |
| --- | --- |
| Can a clean clone run the verifier with no network access? | Yes; otherwise the result is not promotable. |
| Are every input and output hash-pinned in the repository? | Yes; otherwise add them or record the item as pending. |
| Does the command invoke only source-controlled Python and declared packages? | Yes; otherwise move the external program to `external_validators` and build a native primary path. |
| Is an emulator or tool-produced snapshot used? | It is a committed acquisition input with a local extraction/verifier path, not a live-emulation requirement. |
| Is the primary/external distinction explicit in the documentation? | Yes; otherwise add it before promotion. |
