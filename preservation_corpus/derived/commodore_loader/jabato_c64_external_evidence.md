# Jabato C64 Startup: External Evidence Note

> **Evidence class:** P2 — publicly reproducible preservation/catalog observations. This note does not replace retained-byte analysis or controlled emulator measurements.

The retained source-121 image identifies itself as the 1989 Spanish Commodore 64 release of *Jabato vs. Imperio: Libertad*. An independent catalog attributes the release to Aventuras AD, classifies it as a keyboard-controlled graphics/text adventure, and links to releases for Amiga, CPC, Atari ST, MSX, ZX Spectrum, and DOS. This supports treating the observed C64 screen prompt as a keyboard-path loader/runtime question rather than assuming joystick-only interaction.[1]

The Internet Archive item corresponding to the retained `[cr ASS]` C64 release identifies the original emulator extension as `d64` and supplies an externally captured screenshot sequence. Its listed emulator is VICE-resid, providing an independent preservation context for the project’s bounded VICE experiments.[2]

GB64 identifies the release as an ASS-cracked variant in search results, but its live detail page currently presents an anti-automation challenge. It therefore remains a discovery pointer only, not a verified factual source for this research iteration.[3]

**Provenance correction.** Within the project’s authorized release catalog, `[cr ASS]` is treated as a scene/cracker attribution for this artifact variant, not as a game password, command, expected player input, or semantic property of DAAD. The bounded local trial that typed `ASS` is retained only as a negative runtime reproducer: its visible response does not establish a valid startup sequence. The correct next method is byte-level differential comparison against independently retained alternate/original C64 variants, followed by loader/runtime reconstruction.

Planet Emulation independently lists the same `Jabato (1989)(Aventuras AD)(es)[cr ASS]` archive with a reported 73 KiB download size. Its public record exposes no instructions, startup map, or input sequence, so it corroborates release discoverability but does not explain the retained introduction path.[4]

A bounded visual analysis of the public C64 longplay reports a title illustration from approximately 00:00 to 00:07, credits from approximately 00:08 to 00:14, and the playable graphics/text-adventure interface from approximately 00:15. The visible play path then consists of keyboard commands. This is not a byte-identical comparison with the retained ASS-cracked disk, but it establishes that the ordinary game path reaches the parser promptly and makes the retained crack-introduction prompt a variant-specific loader/runtime question rather than a property of the game’s canonical parser interface.[5]

Direct bounded execution of the newly retained Side A TAP variant confirms the same initial progression independently: after tape autostart, its first captured state is the illustrated Jabato title screen; one controlled space input advances to the Spanish Aventuras A.D. credits screen. The retained images are `vice/jabato_side_a_tap_autostart.png` and `vice/jabato_side_a_tap_space.png`. This establishes that the ASS D64 introduction is not required by the observed original Side A title-to-credits path. It does **not** yet prove the complete tape-side load sequence, DDB location, or equivalence of the two media releases.

The credits-stage capture is now reproducible as `vice/jabato_side_a_tap_credits.vsf` (SHA-256 `fb4b3809b962123fe618ee9e119fc532dd5b791e710d317e1ecbb163b96a6c13`) and an exactly extracted 64 KiB `C64MEM` RAM image, `vice/jabato_side_a_tap_credits.ram` (SHA-256 `e2ebd0b931dcab49ea71e2221add54d19d2edaa23ee5fd7fb0dc33f569a7eee6`). After the historical V1 header correction and an embedded-candidate validation correction, the same scan records one verified C64 DAAD V1 DDB at `$3880`, size 24,899 bytes. Its extracted range hashes to `7ffbee6ca3e614011b30261a74022d199ee3345843a0525e92dc9cb5b7bdb5e6`, exactly matching the later playable-state extraction and ADP’s retained Part 1 fixture. The earlier credits-stage negative conclusion was a tooling false negative caused by validating an embedded candidate as though trailing RAM were part of a standalone DDB; it is retained in version history as a reproducer, not as a valid preservation claim.

A separate retained autostart timeline establishes the visible pre-title loader state. Five bounded VICE samples taken during Side A autostart show C64 ROM execution at `$F92C`, `$F995`, `$F999`, and `$E4E7`, followed by execution at `$033D`; the final corresponding screen remains a bordered black loading display rather than the title image. The snapshots and monitor transcripts are retained under `vice/jabato_side_a_tap_loader_timeline_*`. This is compatible with the documented pattern in which a conventional boot stage transfers control to a low-memory turbo/custom loader, but it does not identify a loader family or prove a logical tape-file map.[8]

The retained `$033D` state supplies a concrete custom-loader contract. Its code configures CIA timer A with `$01B6`, reads ten pulse events at a time through `$0334`, rotates timing results through `$FC`, waits for a `$16` synchronization result, then stores four post-sync bytes at `$AC`–`$AF`. It writes payload bytes through `($AC),X` and calls the C64 KERNAL `incsal` (`$FCDB`) and `cmpste` (`$FCD1`) helpers, whose retained source defines `$AC/$AD` as the current `SAL/SAH` destination pointer and `$AE/$AF` as the exclusive `EAL/EAH` end pointer. The analyzer therefore derives each candidate’s header as `end-low, end-high, start-low, start-high`, without assuming a DAAD database header.[8] [9]

The native implementation of that measured contract is retained as `scripts/inspect_cbm_tap.py` and its Side A report as `jabato_side_a_tap_pulse_analysis.json`. Correcting the measured descending `$AC,Y` header store order produces seven complete 256-byte frames that match the captured C64 RAM byte-for-byte. The validated frames occur in physical segments 8–9 and write `$3B80`–`$3C7F`, `$3C80`–`$3D7F`, `$9080`–`$917F`, `$9780`–`$987F`, `$9880`–`$997F`, `$A472`–`$A571`, and `$CA72`–`$CB71`.

The implementation now also follows the original `$03B9 → $03A3` fall-through after a payload reaches its exclusive end pointer: it continues directly into the next descending EAH/EAL/SAH/SAL header rather than searching for another `$16` sync. The retained Side A report records 15 bounded chains comprising 27 candidate frames; the same seven byte-identical blocks remain the only promoted physical recoveries. This strengthened the parser’s executable control-flow fidelity, but it does **not** yet reproduce all 24,899 bytes of Part 1 or establish every custom-stream restart/resynchronization condition. Those work items remain active rather than being inferred from the partial blocks.

The retained credits and playable Side A RAM states both resolve the same Part 1 database at `$3880`. This legacy V1 DDB declares its end at `$99C3`, yielding 24,899 bytes; the credits-state and gameplay-state ranges compare byte-for-byte equal. The materialized gameplay range, `jabato_side_a_tap_second_space_part1.ddb`, validates as Spanish C64 DAAD V1 and has SHA-256 `7ffbee6ca3e614011b30261a74022d199ee3345843a0525e92dc9cb5b7bdb5e6`. It is byte-identical to the retained ADP `JABATO-C64 1.DDB` fixture. The comparison corrected the parser’s V1 interpretation: V1 has eleven section pointers and stores file length at `$001E`, unlike V2’s additional field and `$0020` length. The correction has a real-artifact regression.[10]

### Original Side B and Part 2

The original Side B TAP is now retained separately from Side A as source 249, `249_Jabato_1989_Aventuras_AD_Side_B.zip` (SHA-256 `4756dbe11f03f3065f22d2c0f55ca89601262c2a5514ce75e5d1358fde64a40d`). Its native unpacking emits two parity-valid `JABATO 2` headers and two low-memory loader packets; the latter payloads match the corresponding Side A bootstrap-loader bytes after their conventional packet framing is removed. A bounded controlled-input VICE series proves the original Side B runtime path: its four-second post-input RAM state contains no verified DDB, while the twelve-second and twenty-eight-second states contain the same validated Spanish C64 V1 DDB at `$3880`, length 24,680 bytes. The earliest verified range is materialized as `jabato_side_b_tap_post_input_12_part2.ddb`, SHA-256 `ee3b41f61fc01c27ad776e271f313a2e3fc88875cc9c8e0debebe6904fa48e69`, and is byte-identical to ADP’s retained `JABATO-C64 2.DDB` fixture. The later retained screen reaches the **JABATO EN AFRICA** Aventuras A.D. credit sequence. This closes original-runtime recovery of both C64 DDB parts, while full pulse-only reproduction of Side A and Side B remains active work.[11]

An actual-media VICE watchpoint now qualifies the early Side A transfer path more precisely. Starting from the retained TAP—not a snapshot restoration—a store watch on `$3880`–`$99C2` stops at KERNAL IRQ dispatch `$FF4E`, whose active vector at `$0314` resolves to `$F92C` (`read`) in the retained source map. The source records a three-pulse adaptive reader that recognizes a short-pulse leader, a long byte-start marker, differing short/medium dipole pairs, odd parity, and stores accepted bytes through `STA (SAL),Y`. A bounded native implementation of that state machine recovers four parity-valid physical packets from the early Side A stream: two 202-byte copies of the `JABATO 1` header and two 299-byte copies of the low-memory loader. No packet contains the verified Part 1 DDB prefix. This proves that the first physical units are ROM-readable bootstrap/loader data; it does not yet establish the later payload’s physical framing, adaptive timing, duplicated-block boundaries, or checksum-valid file extraction.[11]

An independently retained public C64 tape-decoder implementation corroborates that exact early result. Pinned revision `e37919fb7107babc590772994fe3e5814a697df4` of `c64tapedecode` emits `jabato 1.p00` from the same original Side A image. After removing its P00 wrapper and two-byte load address, its 289-byte loader payload is byte-identical to the native first-copy KERNAL packet after its nine-byte packet prefix; both normalized ranges hash to `bb002e977409838a8ecb78cfdbf9d12f52087ea01a6a65705d971d0eecda4ddf`. The retained third-party source, diagnostic trace, output, and comparison manifest document that result. Like the native decoder, it emits no later Part 1 database file, which independently reinforces the boundary between verified bootstrap recovery and unresolved custom-payload reconstruction.[12]

Public tool-source research further establishes an important boundary for this blocker. UnDAAD documents itself as obsolete and recommends use principally for early Aventuras AD DOS files; it cannot be used as a proven C64 loader/DDB recovery method.[6] The official DAAD repository instead confirms the full C64, Plus/4, ZX, CPC, MSX, PCW, Atari ST, Amiga, and DOS target matrix, while noting that its compiler is a separate DRC project and that interpreter source is not included. The retained C64 reconstruction must therefore combine its own byte/runtime evidence with the target-aware structural model rather than assume source-level interpreter parity.[7]

### Corrected custom-reader timing boundary

The retained monitor disassembly of the original boot loader at `$0334`–`$03C7` resolves an earlier hypothesis about pulse adaptation. The ROM bootstrap reader and the custom Jabato reader are separate mechanisms. The retained C64 KERNAL `read.s` source adapts its `cmp0` software-servo base after a dipole (`rad3`, lines 121–128), but that behavior applies while the bootstrap executes the KERNAL reader at `$F92C`.

The original Jabato custom reader instead initializes CIA 2 Timer A exactly once per loader entry at `$0378`: `LDA #$B6; STA $DD04; LDA #$01; STA $DD05`. Its bit routine at `$0334` waits for the Datasette FLAG condition in `$DC0D`, arms and observes the CIA state, transfers the resulting carry into `$FC` with `ROR $FC`, and returns. `$034A` invokes the bit routine ten times; `$039F` tests the resulting `$FC` against the `$16` synchronization byte. No instruction in the retained routine modifies the `$01B6` timer latch.

> **Implementation consequence.** The incomplete later-stream recovery cannot be attributed to a missing adaptive threshold in the Jabato custom reader. The existing fixed `$01B6` pulse classifier is directly evidenced. The remaining decoder work must reproduce reader restarts, zero-run/sync acquisition, descending header handling, transfer continuation, and end-of-block control flow. The KERNAL software-servo remains relevant only to complete physical reconstruction of the earlier ROM bootstrap packets.
